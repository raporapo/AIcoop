# 開発の進め方

## テスト駆動のサイクル

1. 設計書（`docs/design.md`）から、作る節の「仕様」と「受け入れ条件」を選ぶ。
2. 受け入れ条件を1つずつテストに書く。`pnpm test:watch` で**失敗するのを確かめる**（Red）。
3. 通る最小の実装を書く（Green）。
4. 緑のまま整える（Refactor）。`pnpm verify` が通ったらコミットする。

テストの名前には設計書の節番号を入れて、「どの決定を守るテストか」を追えるようにする。

## 設計書に記録が必要な決定（未記録）

実装の途中で、設計書に書かれていない判断が必要になったもの。オーナーが決めたら第18章に追記し、本文を直してから、ここから消す。

| # | 内容 | いまの実装 | 理由 |
|---|---|---|---|
| 1 | 解釈が分かれるパス（`.`・`..` の区切り、`%2e`・`%2f`・`%5c`、`\`、制御文字）の扱い | どの操作にも一致させない → `deny`（`no_operation`） | 外のサーバーがパスを正規化すると、判定したものと違うリソースに届く（例：`/repos/myorg/app/../../other/secret`）。P-3 |
| 2 | `web.read` の `*` が、ループバック・プライベート・リンクローカルのアドレス（`127.0.0.1:7070` の制御サーバーのAPI、ComfyUI、LAN、クラウドのメタデータ）を含むか | 未対応（ホスト名だけでは判定できない） | 箱からホストの内側へ届いてしまう恐れ。名前解決のあとのアドレスで弾く必要があり、資格プロキシ（daemon）側で決める |
| 3 | 許可項目がパラメーターを制限しているのに、その操作のパスにそのパラメーターがない | 一致しない → `deny` | 拒否側に倒す（P-3） |
| 4 | パラメーターの glob の大文字・小文字 | 区別する | GitHub の owner/repo は大文字・小文字を区別しないが、区別しても拒否側に倒れるだけで許可は広がらない |
| 5 | HTTPメソッドの大文字・小文字 | 区別する（`get` は `GET` に一致しない） | 拒否側に倒す |
| 6 | 設定の誤りのメッセージの言語 | zod の既定（英語）＋独自のものは日本語 | 11.7 では CLI の表示は日本語。`aicoop check` を作るときに zod の日本語ロケールを使うか決める |
